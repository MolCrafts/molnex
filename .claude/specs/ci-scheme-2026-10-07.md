# MolCrafts CI scheme (2026-10-07, binding for every MolCrafts repo)

The user asked: "清理、拆分ci；ci按照类型分成不同文件，然后用job区分哪些在fork、upstream 跑，哪些在master、dev或者其他功能分支跑。精简！泛化" — clean up and split CI, one file per kind of work, gate jobs by fork vs upstream and by branch, keep it lean and general. They then added: "同理，拆分其他所有的mol* 仓库的ci，设置所有仓库的master分支的保护" — split CI the same way in every other mol* repo, and protect `master` in every repo.

## Files
Use one file per kind of work, with the same file names in every repo. Leave out any file a repo doesn't need.

| file | what | triggers |
|---|---|---|
| `lint.yml` | format, linters (clippy / ruff incl. PLW1514 / eslint / biome …), type checks, lock checks, partner-resolve check; fast | push `**`, pull_request → dev/master/main, workflow_dispatch |
| `test.yml` | unit and integration tests, every language and binding, cross-repo conformance | same as `lint.yml` |
| `docs.yml` | strict docs build everywhere; deploy upstream-only | same, plus deploys gated |
| `nightly.yml` | scheduled; extended matrices, coverage, snapshots, benchmarks | schedule + workflow_dispatch; upstream-only |
| `release.yml` | publishing (crates.io, PyPI, npm, VS Code marketplace, GitHub Release, site deploys tied to releases), one file; `workflow_dispatch` dry-run (build, no upload) | `v*` tags + workflow_dispatch; upload upstream-only |

Repo-specific deploy workflows, such as web or API deploys, fold into `docs.yml` or `release.yml` when they are release- or docs-like. Otherwise they go into one `deploy.yml`, upstream-only. Nothing else stays.

## Contexts and gating
Gating uses job-level `if:` with the same expressions in every repo.
- **Upstream:** `github.repository_owner == 'MolCrafts'`.
- **Integration ref:** `dev`, `master`, `main`, or a PR into one of them.
- **Feature ref:** everything else.

What runs where:
- **Feature branches** (fork or upstream): lint, the fast test tier (Linux, one Python/Node version, core tests) and the docs build.
- **Integration refs** (fork or upstream): the full tier (OS matrix linux/macos/windows where the project supports them, every binding, feature matrix, conformance).
- **Upstream only:** deploys, publishing, snapshot submission, anything that needs org secrets, and nightly.

Run each commit only once. Skip a `pull_request` run when the head repo is the base repo (the push already covers it):
`if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name != github.repository`.

Concurrency is one group per workflow and ref. Cancel in-progress runs on feature refs only.

## Generalize
- Shared setup lives in local composite actions under `.github/actions/<name>/action.yml`, with the same names and interface across repos: `setup-rust`, `setup-python`, `setup-node`, `setup-partners`.
- Job names are short and stable: `<area> / <what>`.

## Master protection (every MolCrafts repo)
Each repo gets one repository ruleset, `protect-master`, on the default branch (`~DEFAULT_BRANCH`, i.e. master or main). It contains:
- `deletion` (blocked);
- `non_fast_forward` (no force push);
- `pull_request` (PR required, 0 approvals, because the user merges their own PRs);
- `required_status_checks` with the repo's full-tier job names (strict: false), only for checks that exist and pass.

No bypass actors. An existing ruleset gets updated, not duplicated.

## Landing (binding)
- Push to the Roy-Kid fork first. Fork it with `gh repo fork MolCrafts/<repo> --clone=false` if no fork exists.
- Get the fork CI green on the branch, and then on an in-fork PR for the integration tier.
- Only then open a PR to MolCrafts. Merge only when it is green, and never merge a red PR.
- Never push branches straight to MolCrafts, and never use `--no-verify`.

## Revision 2 (harmonization, binding; supersedes the dedup and tier rules above)
The three groups' first pass diverged. These are the canonical rules, taken from the molrs implementation.

**Tiers**
- **Full tier** runs on:
  - every push to a fork (fork-first means the full tier is proven before the PR);
  - pushes to `dev` / `master` / `main` on MolCrafts;
  - `v*` tags;
  - `workflow_dispatch`.
- **Fast tier** runs only on feature-branch pushes to MolCrafts.

**Tier decision.** One `tier` job per `test.yml` computes the tier, and every test job reads its output. The job is named `test / tier`. The rule:
`full = github.repository_owner != 'MolCrafts' || contains(fromJSON('["dev","master","main"]'), github.ref_name) || github.event_name != 'push' || startsWith(github.ref, 'refs/tags/')`

**Dedup.**
- A PR is skipped only when it is inside a fork, i.e. `head repo == base repo && owner != 'MolCrafts'`, because the fork push already ran the full tier.
- Same-repo PRs on MolCrafts, such as Dependabot's, run, so their required checks appear.
- The workflow-level guard used in lint/test/docs:
  `if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name != github.repository || github.repository_owner == 'MolCrafts'`

**Shared composite actions** live once, in MolCrafts/molcrafts-ci: `actions/setup-python`, `setup-node`, `setup-rust` and `setup-partners`, used as `MolCrafts/molcrafts-ci/actions/<name>@master` (molcrafts-ci `master` is their dev line). Repos delete their local copies. Repo-specific actions stay local (`setup-wasm`, `build-registry`, `setup-registry`).

**Concurrency.** Every workflow file (lint, test, docs, nightly, release, deploy) has exactly this top-level block, with `<file>` the file's basename (`lint`, `test`, `docs` …):
```yaml
concurrency:
  group: <file>-${{ github.workflow }}-${{ github.event_name }}-${{ github.ref }}
  cancel-in-progress: ${{ !contains(fromJSON('["refs/heads/dev","refs/heads/master","refs/heads/main"]'), github.ref) && !startsWith(github.ref, 'refs/tags/') }}
```
(`cancel-in-progress: false` for nightly, release and deploy.) Why: `release.yml` runs `lint.yml` and `test.yml` through `workflow_call`, and a called workflow's own `concurrency` is evaluated in the caller's context. With the old `lint-${{ github.event.pull_request.number || github.ref }}`, a `workflow_dispatch` dry run on a feature branch put its called lint/test into the same `lint-<ref>` / `test-<ref>` group as that branch's push run and, since the ref is a feature ref, cancelled it. In a called workflow `github.workflow` and `github.event_name` are the caller's (`release`, `workflow_dispatch`), so the group now differs from the direct push run (`lint`, `push`); the `<file>` literal keeps the called lint and test apart from each other. Job-level groups (e.g. a single `docs-deploy` slot) are unaffected.

**Required checks.** `test / tier` plus the full-tier job names. Required checks are only added after a green run under those names on a PR into the default branch, or on the default branch itself.

## Revision 3 (ci-context, binding; supersedes the tier job, the dedup guard and the inline upstream gates of Revision 2)
The rules of Revision 2 are unchanged. Where they live changes: one composite action in MolCrafts/molcrafts-ci decides them, so changing a rule is one pull request there instead of one per repository.

**The action.** `MolCrafts/molcrafts-ci/actions/ci-context@master`.
- Inputs: `owner`, `repository`, `event-name`, `ref`, `pr-head-repository`. Each defaults to the run's own github context (`github.repository_owner`, `github.repository`, `github.event_name`, `github.ref`, `github.event.pull_request.head.repo.full_name`). Workflows pass none; the inputs exist so the rules can be tested against synthetic contexts.
- Outputs, as the strings `"true"`/`"false"` except `tier`:

| output | value |
|---|---|
| `tier` | `fast` only for a feature-branch push to MolCrafts; `full` otherwise (every fork run, dev/master/main and tags upstream, pull requests, dispatches, schedules) |
| `upstream` | the owner is MolCrafts |
| `integration` | the ref is `refs/heads/dev`, `master`, `main` or `refs/tags/*` |
| `skip-pr` | a `pull_request` whose head repo is the base repo, outside MolCrafts (an in-fork PR; its push already ran the full tier) |
| `cancel` | not `integration` (a feature ref, PRs included) |

The rules live in `actions/ci-context/context.sh`.

**The context job.** Every workflow file (lint, test, docs, nightly, release, deploy) starts with this job, verbatim except `<file>`:
```yaml
  # Where this run happens, decided once: MolCrafts/molcrafts-ci/actions/ci-context.
  context:
    name: <file> / context
    runs-on: ubuntu-latest
    outputs:
      tier: ${{ steps.context.outputs.tier }}
      upstream: ${{ steps.context.outputs.upstream }}
      integration: ${{ steps.context.outputs.integration }}
      skip-pr: ${{ steps.context.outputs.skip-pr }}
      cancel: ${{ steps.context.outputs.cancel }}
    steps:
      - id: context
        uses: MolCrafts/molcrafts-ci/actions/ci-context@master
```
The job is named per file (`lint / context`, `test / context`, …), not `ci / context`, because one shared name across several workflows makes a required check ambiguous. molcrafts-ci alone runs it from its own checkout (`./actions/ci-context` after a sparse checkout), so a rule change is exercised before any repository follows `@master`.

**Gates.** Every other job reads `needs.context.outputs.*`:
- The dedup: every root job of a `pull_request`-triggered workflow has `needs: context` and `if: needs.context.outputs.skip-pr != 'true'`. Jobs that need a gated job are skipped transitively.
- The tier: `needs.context.outputs.tier == 'full'` (matrices, full-only jobs). The `test / tier` job is gone.
- Upstream-only work (deploys, publishing, snapshot submission, org secrets, nightly): `needs.context.outputs.upstream == 'true'`, in job and step `if:`, job `env:`, `environment:` and job-level `concurrency`. A workflow-level `env:` that depended on the owner (e.g. `PUBLISH`) moves into the env of the jobs that read it.
- No workflow inlines `github.repository_owner` or the Revision 2 expressions any more.

**What stays inline** (expressions there cannot read job outputs, or they are per-repo by nature), identical in every repo: the `on:` triggers, the workflow-level `concurrency` block of Revision 2, and the job matrices.

**Required checks.** `test / context` replaces `test / tier` in `protect-master` and `require-green-ci`. In molcrafts-ci, the `test / ci-context (<case>)` jobs are required as well.

**Tests** (molcrafts-ci). `test / ci-context (<case>)` calls the action with 13 synthetic contexts and asserts all five outputs: fork feature push, fork dev push, upstream feature/dev/master push, PR from a fork, same-repo PR upstream, in-fork PR, PR into a fork from another fork, upstream tag, dispatch upstream and in a fork, and upstream schedule. Each case also calls the action with no inputs and checks the outputs against the Revision 2 inline expressions on the live run. `tests/test_ci_context.py` runs the same table, read from test.yml, through `context.sh`, plus missing-input and deleted-fork cases. A change to the action must pass these before it reaches `master`, which every repository follows.

## Revision 4 (publish, the validator; binding; supersedes the `cancel` output of Revision 3 and the concurrency comment of Revision 2)
Four gaps before the molrs/molpy 0.16 release: `cancel` could never be read, a root job could silently lack its `skip-pr` gate, the Revision 2 concurrency comment about `workflow_call` was copied into workflows nobody calls, and upload jobs tested only `github.event_name == 'push'`, so a branch trigger added to `release.yml` would publish.

**`publish` replaces `cancel`.** `actions/ci-context` outputs:

| output | value |
|---|---|
| `tier`, `upstream`, `integration`, `skip-pr` | unchanged (Revision 3) |
| `publish` | `"true"` only when the owner is MolCrafts, the event is `push` and the ref is `refs/tags/v*`; false for a fork's tag, any branch (master included), a dispatch (the dry run), a schedule and a non-`v` tag |

`cancel` is gone: a workflow-level `concurrency:` cannot read `needs`, so nothing could consume it, and it was a second copy of the feature-ref rule. No repository read `needs.context.outputs.cancel` (checked on dev/master of all 19). A context job that still maps `cancel: ${{ steps.context.outputs.cancel }}` gets an empty string and keeps working; the validator flags the line.

**The context job** (replaces the Revision 3 template; verbatim except `<file>`):
```yaml
  context:
    name: <file> / context
    runs-on: ubuntu-latest
    outputs:
      tier: ${{ steps.context.outputs.tier }}
      upstream: ${{ steps.context.outputs.upstream }}
      integration: ${{ steps.context.outputs.integration }}
      skip-pr: ${{ steps.context.outputs.skip-pr }}
      publish: ${{ steps.context.outputs.publish }}
    steps:
      - id: context
        uses: MolCrafts/molcrafts-ci/actions/ci-context@master
```

**The publish gate.** Every job that uploads to a registry (PyPI, crates.io, npm, VS Code marketplace / Open VSX), deploys to a registry, or creates or uploads to a GitHub Release has `if: needs.context.outputs.publish == 'true'` (as a top-level `&&` conjunct) and tests no raw `github.event_name` / `github.ref` / `github.ref_name` / `github.ref_type` in its `if`, `environment`, `env`, or any step's `if` / `env`. `environment:` becomes the plain name (`environment: pypi`), since the job only runs when publishing. A job that both dry-runs and publishes (pack on dispatch, publish on tag) splits: the dry run stays in the build job, the upload job is publish-gated. Tag-only docs or site deploys may gate on `publish` too. The one exception is `nightly.yml`, whose nightly channel (e.g. `molcrafts-molrs-nightly`) publishes from a branch, not a tag: its upload jobs gate on `needs.context.outputs.upstream == 'true'`.

**The canonical concurrency block** (defined once, in `actions/check-workflows/check_workflows.py`):
```yaml
concurrency:
  group: <file>-${{ github.workflow }}-${{ github.event_name }}-${{ github.ref }}
  cancel-in-progress: ${{ !contains(fromJSON('["refs/heads/dev","refs/heads/master","refs/heads/main"]'), github.ref) && !startsWith(github.ref, 'refs/tags/') }}
```
`cancel-in-progress: false` in `nightly.yml`, `release.yml` and `deploy.yml`. The comment above it explains `workflow_call` only in a file that has that trigger (lint, test); elsewhere it is one line, e.g. `# One group per file, workflow, event and ref; only a feature ref cancels its superseded runs.`

**The validator.** `MolCrafts/molcrafts-ci/actions/check-workflows@master`, a composite action running a PEP 723 script through `uv run --script` (no global Python). Every repository runs it in `lint.yml`:
```yaml
  workflows:
    name: lint / workflows
    needs: context
    if: needs.context.outputs.skip-pr != 'true'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: MolCrafts/molcrafts-ci/actions/check-workflows@master
```
It reads every `.github/workflows/*.yml` and prints `file:line: job <id>: [rule] message` per violation (plus `::error` annotations in Actions), exit 1 on any:

| rule | check |
|---|---|
| `context` | first job `context`, named `<file> / context`, a step `id: context` with `uses: MolCrafts/molcrafts-ci/actions/ci-context@master` (molcrafts-ci alone: `./actions/ci-context`), outputs exactly the action's outputs (read from its `action.yml`) |
| `needs` | every other job reaches `context` through `needs` (transitively) |
| `skip-pr` | in a workflow that can run for a pull request (`pull_request`, `pull_request_target`, `workflow_call`), every job is skipped on an in-fork PR: its `if` has a top-level conjunct `needs.context.outputs.skip-pr != 'true'`, or one implying it (`upstream == 'true'`, `publish == 'true'`, an `event_name` test excluding `pull_request`), or it needs a job that is so skipped and its `if` has no `always()` / `cancelled()` (which run past a skipped need). A `tier == 'full'` gate alone is not enough. |
| `publish` | the publish gate above; uploads are detected by `environment:`, `pypa/gh-action-pypi-publish`, `cargo publish` / `npm publish` / `pnpm publish` without a literal `--dry-run` (one inside `${{ }}` is conditional, so it counts as publishing), `vsce` / `ovsx publish`, `softprops/action-gh-release`, `gh release create` / `upload` |
| `concurrency` | the canonical block, exactly |
| `pin` | `MolCrafts/molcrafts-ci/actions/*` at `@master`, in workflows and `.github/actions/*/action.yml` |
| `comment` | no comment mentions `workflow_call` in a workflow without that trigger |
| `name` | every job except a reusable-workflow call is named `<file> / <what>` (area = the file stem) |

Tests in molcrafts-ci: one good and one bad fixture repository per rule (`tests/fixtures/check-workflows/<rule>/{good,bad}`), the bad one asserting exactly its rule's violations; expression parsing (conjuncts, parentheses, `||`, string literals); transitive skipping; publish command detection; molcrafts-ci's own workflows pass. `ci-context`'s table grows to 16 cases (fork tag, upstream non-`v` tag, upstream dispatch on a tag) asserting `publish`, and the live step checks `publish` against `owner == MolCrafts && event == push && startsWith(ref, 'refs/tags/v')`.

**Rollout** (step 2, every repository): map `publish` and drop `cancel` in each context job; gate every upload on `publish`; fix the concurrency comment; add `lint / workflows`; make the validator green; add `lint / workflows` to `protect-master` after its first green run on a PR into the default branch.
